# 実装順序ガイド

`docs/plan.md` で洗い出した機能を、どの順番で作るとよいかをまとめる。基本方針は「土台(認証・DB)→ 社員が使う最小機能 → 管理者が使う機能 → 仕上げ」の順。各ステップは前のステップの成果物に依存するため、上から順に進めることを推奨する。

## フェーズ0: 土台づくり

### 1. プロジェクトスキャフォールド
- `create-next-app`(TS / App Router / Tailwind)
- Prisma + SQLite + bcryptjs + zod を導入
- **理由**: 以降すべての作業の前提。ここが無いと何も動かせない。

### 2. データモデル定義
- `prisma/schema.prisma` に `User` / `Session` / `AttendanceRecord` / `CorrectionRequest` を定義
- マイグレーション実行、`seed.ts` で初期管理者アカウントを1件作成
- **理由**: 画面より先にデータ構造を固めることで、後続の実装で手戻りが起きにくい。管理者アカウントがないとログイン画面すら検証できない。

### 3. 認証(ログイン/ログアウト・セッション・middleware)
- ログイン画面、パスワード検証、Cookieセッション発行
- `proxy.ts` で未ログイン時のリダイレクト
- **理由**: 打刻もCRUDも「誰がやったか」が前提になる機能のため、他の画面より先に必要。ここまでで「管理者アカウントでログインできる」状態が確認できる。

## フェーズ1: 社員が使う最小機能(MVPのコア)

### 4. 社員ダッシュボード(出勤・退勤・休憩ボタン)
- 当日の `AttendanceRecord` を取得/作成し、状態に応じてボタンの活性・非活性を切り替え
- **理由**: 勤怠管理アプリの主目的そのもの。これが動けば「打刻して記録が残る」という最小価値を確認できる。

### 5. 自分の月次履歴画面
- ログイン中の社員の `AttendanceRecord` を月単位で一覧表示
- **理由**: 打刻データを可視化して確認できないと、打刻機能が正しく動いているか検証しづらい。実装コストが低い割に確認価値が高いので早めに着手。

### 6. 打刻修正申請(社員側: 申請フォーム・自分の申請一覧)
- `CorrectionRequest` の作成、自分の申請ステータス確認
- **理由**: 承認側(フェーズ2)を作る前に、申請データを作れる状態にしておく必要がある。

ここまで完了すると、社員側の機能は一通り揃い、単独のロールでアプリを一巡できる。

## フェーズ2: 管理者が使う機能

### 7. 社員CRUD
- 社員の登録・編集・無効化
- **理由**: 本来はフェーズ0直後でも良いが、`seed.ts` で暫定の社員データを用意できるため後回しにしてもフェーズ1の検証は可能。実運用に向けては、複数社員でのテストの前に必要になる。

### 8. 打刻修正申請の承認キュー
- 申請一覧の表示、承認/却下、承認時に `AttendanceRecord` へ反映
- **理由**: フェーズ1-6で作った申請データを消費する機能なので、申請機能より後に作るのが自然。

### 9. 月次勤怠一覧・CSVエクスポート
- 社員別・月別の集計表示とCSVダウンロード
- **理由**: 給与計算という「最終成果物」を出す機能のため、打刻・修正のデータが揃った後に作るのが効率的。CSVの中身を目視確認する際、打刻データが十分にある方がテストしやすい。

## フェーズ3: 仕上げ

### 10. 入力バリデーション・エラー表示・スタイリング・README
- zodによるフォームバリデーション強化
- エラーメッセージ、レスポンシブ対応
- セットアップ手順をREADMEに記載
- **理由**: 機能が一通り揃ってから磨く方が、手戻りなく仕上げに集中できる。

## 全体の依存関係(概略)

```
1 スキャフォールド
  └─ 2 データモデル
       └─ 3 認証
            ├─ 4 社員ダッシュボード(打刻)
            │    └─ 5 自分の月次履歴
            │    └─ 6 修正申請(社員側)
            │         └─ 8 承認キュー(管理者側)
            └─ 7 社員CRUD
                 └─ 9 月次一覧・CSV出力
                      └─ 10 仕上げ
```

## 検証のマイルストーン

- **フェーズ0完了時**: 管理者アカウントでログインできる
- **フェーズ1完了時**: 1人の社員として、打刻→履歴確認→修正申請の一連が動く
- **フェーズ2完了時**: 管理者として、社員登録→申請承認→CSV出力までの一連が動く
- **フェーズ3完了時**: バリデーション・表示崩れ・READMEを確認し、リリース可能な状態
